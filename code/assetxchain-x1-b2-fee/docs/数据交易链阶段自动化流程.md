# 数据交易链阶段自动化流程

## 1. 适用范围

本文档定义 AssetXChain 数据交易链补充工作的自动化执行流程。

当用户在对话中提出类似以下请求时，应按本文档执行：

```text
完成阶段 1
完成阶段一
继续阶段 2
按照计划补充阶段 3
实现数据交易链项目补充计划中的阶段 4
```

阶段内容以 `docs/数据交易链项目补充计划.md` 为唯一计划依据。执行前必须先阅读该文件，再根据用户指定阶段完成对应任务。

## 2. 总体原则

执行阶段任务时必须遵守以下原则：

- 先读计划，再读代码，不凭记忆实现。
- 每次只完成用户指定的阶段；若用户明确要求多个阶段，则按阶段顺序逐个完成。
- 不修改与当前阶段无关的源码、实验文件或文档。
- 不覆盖用户已有未提交改动。
- 发现工作区已有改动时，先用 `git status --short` 和必要的 `git diff` 判断是否与当前阶段相关。
- 若已有改动与当前阶段相关，则基于已有改动继续，不回滚。
- 若已有改动与当前阶段无关，则忽略，不纳入本阶段提交。
- 实现功能前优先补测试或更新现有测试。
- 完成后运行该阶段最小必要验证。
- 完成后只提交本阶段产生或修改的文件。
- 提交信息格式必须为：

```text
l+ 工作内容
```

例如：

```sh
git commit -m "l+ implement certificate market transfer extension"
```

## 3. 标准执行流程

当用户要求完成某个阶段时，按以下流程执行。

### 3.1 读取计划

首先读取：

```text
docs/数据交易链项目补充计划.md
```

确认用户指定阶段对应的：

- 阶段目标。
- 修改范围。
- 设计内容。
- 验收标准。
- 推荐测试命令。

如果用户指定的阶段不存在，应停止并向用户说明。

### 3.2 检查工作区

执行：

```sh
git status --short
```

如果存在未提交改动：

- 判断是否与当前阶段相关。
- 相关改动：继续读取 diff 并在其基础上工作。
- 无关改动：不得修改、不得暂存、不得提交。

必要时读取：

```sh
git diff -- <path>
```

### 3.3 读取相关代码

根据计划中的修改范围读取相关文件。

优先使用：

```sh
rg
sed
find
```

不要只根据文件名猜测逻辑。需要确认：

- 当前接口。
- 当前测试。
- 当前错误码。
- 当前事件。
- Runtime 配置。
- 合约绑定。
- 相关 trait 依赖。

### 3.4 制定阶段内小计划

在开始编辑前，列出本阶段的最小任务拆分。

每个阶段一般包括：

1. 补充或调整测试。
2. 实现最小功能。
3. 更新必要文档或注释。
4. 运行验证。
5. 检查 diff。
6. 提交。

### 3.5 先写测试

除纯文档阶段外，应优先补充测试。

测试应覆盖：

- 成功路径。
- 权限失败。
- 状态不存在。
- 重复调用。
- 失败不产生错误状态。
- 事件或统计是否正确。

如果某个阶段暂时无法编写自动化测试，应在最终回复中明确说明原因，并至少提供可执行的手动验证步骤。

### 3.6 实现功能

实现应遵守：

- 使用项目现有模式。
- 保持修改范围最小。
- 避免无关重构。
- 避免引入新的全局设计，除非计划文件明确要求。
- 保持 Runtime、pallet、contract 的接口语义一致。

### 3.7 运行验证

根据阶段运行最小必要命令。

常用命令：

```sh
cargo test -p pallet-dataassets
cargo test -p pallet-markets
cargo test -p market-standard
cargo test -p market-orderbook
cargo test -p assetxchain-runtime
cargo check -p assetxchain-node
```

如果修改实验脚本，应运行对应脚本或测试。

如果验证失败，应先修复本阶段引入的问题。若失败来自无关既有问题，应记录清楚。

### 3.8 检查 diff

执行：

```sh
git diff -- <本阶段相关文件>
```

确认：

- 没有无关文件。
- 没有格式化造成的大范围无关变更。
- 没有把生成物、链数据、target、node_modules 纳入修改。
- 没有覆盖用户已有无关改动。

### 3.9 暂存本阶段文件

必须显式暂存本阶段文件，不允许使用 `git add .`。

示例：

```sh
git add runtime/src/asset_market_extension.rs
git add contracts/market_standard/lib.rs
git add pallets/dataassets/src/lib.rs
git add pallets/dataassets/src/tests.rs
```

如果本阶段新增实验文件，也逐个路径暂存。

### 3.10 提交

完成阶段任务后提交。

提交命令格式：

```sh
git commit -m "l+ 工作内容"
```

提交信息应简短描述本阶段完成的核心工作。

示例：

```sh
git commit -m "l+ implement certificate transfer chain extension"
git commit -m "l+ add market order state machine"
git commit -m "l+ record data trade settlements"
git commit -m "l+ wire market trading incentives"
```

### 3.11 最终回复

提交后向用户汇报：

- 完成了哪个阶段。
- 修改了哪些核心文件。
- 运行了哪些验证。
- commit hash 和提交信息。
- 是否存在未完成风险或后续阶段依赖。

## 4. 阶段执行细则

以下细则来自 `docs/数据交易链项目补充计划.md`，执行时仍必须回到原文件确认完整要求。

### 4.1 阶段 1：权证交易 Chain Extension

目标：

```text
让市场合约不仅能交易数据资产元证，也能交易 RightToken 权证。
```

执行要点：

- 实现 Runtime 中 `TRANSFER_CERT_FUNC_ID = 2`。
- 补充合约侧 `transfer_certificate` 绑定。
- 调用 `pallet-dataassets` 的权证转移内部逻辑。
- 明确非持有人、证书不存在、证书状态非法时的错误返回。
- 更新或新增测试，验证成功和失败路径。

建议验证：

```sh
cargo test -p pallet-dataassets
cargo test -p market-standard
cargo test -p market-orderbook
cargo test -p assetxchain-runtime
```

提交示例：

```sh
git commit -m "l+ implement certificate transfer chain extension"
```

### 4.2 阶段 2：市场订单状态机

目标：

```text
将市场订单从 active 布尔值扩展为完整交易状态机。
```

执行要点：

- 增加订单状态：`Listed`、`Locked`、`Settled`、`Cancelled`、`Failed`。
- 支持元证订单和权证订单。
- 订单包含卖方、买方、价格、资产类型、资产 ID、权证 ID、状态和时间字段。
- 购买流程中确保 Runtime 结算失败不会错误删除订单。
- 撤单失败不得使用 `panic!`，应返回错误。

建议验证：

```sh
cargo test -p market-orderbook
cargo test -p market-standard
```

提交示例：

```sh
git commit -m "l+ add market order state machine"
```

### 4.3 阶段 3：链上交易结算记录

目标：

```text
为数据交易链提供统一的链上结算证据。
```

执行要点：

- 新增或补充 `TradeSettled` 事件。
- 记录 trade_id、market、seller、buyer、asset_id、certificate_id、asset_type、price、settled_at。
- 元证交易成功产生 `AssetTransferred` 和 `TradeSettled`。
- 权证交易成功产生 `CertificateTransferred` 和 `TradeSettled`。
- 失败交易不得产生结算事件。

建议验证：

```sh
cargo test -p pallet-dataassets
cargo test -p market-orderbook
cargo test -p assetxchain-runtime
```

提交示例：

```sh
git commit -m "l+ record data trade settlements"
```

### 4.4 阶段 4：市场统计与激励

目标：

```text
将真实成交行为接入市场、交易者和资产激励统计。
```

执行要点：

- 扩展 `IncentiveHandler`。
- 记录市场月交易额。
- 记录交易者月交易额。
- 修复优质市场奖励中的 placeholder 运营者查找。
- 奖励失败不能错误中断正常交易。

建议验证：

```sh
cargo test -p pallet-incentive
cargo test -p pallet-markets
cargo test -p pallet-dataassets
cargo test -p assetxchain-runtime
```

提交示例：

```sh
git commit -m "l+ wire market trading incentives"
```

### 4.5 阶段 5：轻量交付证明闭环

目标：

```text
为交易后的链下数据交付提供可追踪凭据。
```

执行要点：

- 不实现完整 IPFS 可用性证明。
- 保留或查询 `metadata_cid`、`data_cid`、`encryption_info`。
- 增加交付确认事件或接口。
- 交付确认可与 `trade_id`、`asset_id` 或 `certificate_id` 关联。

建议验证：

```sh
cargo test -p pallet-dataassets
cargo check -p assetxchain-node
```

提交示例：

```sh
git commit -m "l+ add lightweight delivery confirmation"
```

### 4.6 阶段 6：第二篇论文实验套件

目标：

```text
建立 paper_exp/paper2_exp，为第二篇论文提供可复现实验。
```

执行要点：

- 新建 `paper_exp/paper2_exp`。
- 增加实验 README、runner、测试和 CSV 输出目录。
- 覆盖交易开销、一致性异常、权证市场扩展、激励统计。
- 输出字段应能直接用于论文表格和图。

建议验证：

```sh
cd ../paper_exp/paper2_exp
npm test
node scripts/preflight.js
```

如果没有 Node 测试框架，应至少提供可运行 smoke 脚本。

提交示例：

```sh
git commit -m "l+ add paper2 data trading experiments"
```

## 5. 多阶段执行规则

如果用户要求一次完成多个阶段，例如：

```text
完成阶段 1 到阶段 3
```

则必须：

1. 按阶段 1、阶段 2、阶段 3 的顺序执行。
2. 每个阶段独立测试。
3. 每个阶段独立提交。
4. 不把多个阶段混在一个 commit 中。

如果后续阶段依赖前一阶段，而前一阶段失败，应停止并报告原因。

## 6. 阻塞处理

遇到以下情况时，应暂停实现并向用户说明：

- 计划文件与当前代码严重不一致。
- 用户指定阶段存在多种互斥设计，无法安全假设。
- 工作区已有相关改动但意图不明，继续修改可能覆盖用户工作。
- 必要测试无法运行，且无法通过代码阅读确认安全性。
- 阶段任务明显超出当前计划范围。

说明时应给出：

- 阻塞位置。
- 已确认的事实。
- 可选处理方式。
- 推荐下一步。

## 7. 禁止事项

执行本流程时禁止：

- 未阅读 `docs/数据交易链项目补充计划.md` 就开始实现。
- 使用 `git add .`。
- 提交无关文件。
- 提交 `target/`、链数据、`node_modules/`、临时日志或生成二进制。
- 回滚用户已有改动。
- 把多个阶段混成一个提交。
- 为了通过测试删除现有功能。
- 在未说明的情况下跳过验证。

## 8. 最终完成标准

一个阶段只有同时满足以下条件，才视为完成：

- 阶段计划中的核心功能已实现。
- 成功路径和关键失败路径有测试或明确验证。
- 最小必要验证已运行。
- diff 已检查且只包含本阶段相关文件。
- 本阶段文件已显式暂存。
- 已提交 commit，且提交信息以 `l+` 开头。
- 最终回复中说明修改、验证和剩余风险。
