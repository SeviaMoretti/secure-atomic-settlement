# 数据交易链项目补充计划

## 1. 目标

本文档用于指导 AssetXChain 面向第二篇论文的数据交易链能力补充。

补充目标是将当前项目从“数据资产确权与市场雏形”推进为可支撑论文实验的数据交易链 MVP，形成如下完整流程：

```text
数据资产注册 -> 市场授权 -> 资产/权证上架 -> 买方购买
-> Runtime 可信结算 -> 元证/权证状态更新 -> 交易统计与激励记录
-> 可追踪交付与异常处理
```

该补充计划服务于论文方向：

```text
AssetXChain：一种面向数据资产可信流通的合约-运行时协同数据交易链
```

核心创新主线为：

- 市场合约负责订单、撮合、支付等可编程交易逻辑。
- Runtime 负责元证和权证的可信权属结算。
- 元证 MetaToken 和权证 RightToken 分离，支持所有权交易和细粒度使用权交易。
- 授权、结算、统计、激励和追责形成链上闭环。

## 2. 当前项目基础

当前 AssetXChain 已具备以下基础能力：

- `pallet-dataassets`：数据资产注册、元证转移、权证发行、权证转移、市场授权、资产状态根计算。
- `pallet-markets`：市场合约注册、市场合约标准验证、市场运营者质押。
- `contracts/market_standard`：市场标准接口和数据资产 Chain Extension 合约绑定。
- `contracts/market_orderbook`：固定价格订单簿市场原型。
- `runtime/src/asset_market_extension.rs`：合约调用 Runtime 进行元证转移的链扩展。
- `pallet-incentive`：首次创建奖励、优质数据奖励、市场奖励、交易者返还、流动性奖励等激励框架。
- `pallet-collaterals`：市场运营者、IPFS 服务商、治理质押等多角色质押与罚没框架。
- `pallet-storage_ipfs`：链下存储订单、服务商注册、存储绑定、存储证明的原型模块。

当前主要缺口：

- 权证交易的 Chain Extension 尚未实现。
- 市场订单状态过于简单，无法支撑完整交易状态机。
- 缺少统一的链上结算记录。
- 市场交易额、交易者交易额与激励模块尚未完全打通。
- `storage_ipfs` 尚未接入 Runtime，链下交付闭环仍是原型。
- 缺少完整端到端实验脚本。

## 3. 总体补充路线

项目补充按七个阶段推进：

1. 补齐权证交易 Chain Extension。
2. 完善市场订单状态机。
3. 增加链上交易结算记录。
4. 打通市场统计与激励。
5. 补充轻量交付证明闭环。
6. 建立第二篇论文实验套件。
7. 打通合约订单状态与 Runtime 结算一致性闭环。

建议优先实现阶段 1 至阶段 4，以形成数据交易链核心闭环；阶段 7 用于补齐合约订单状态与 Runtime 结算记录之间的一致性证据；阶段 5 可作为论文增强项；阶段 6 用于支撑论文实验结果。

## 4. 阶段 1：补齐权证交易 Chain Extension

### 4.1 目标

让市场合约不仅能交易数据资产元证，也能交易 RightToken 权证。

当前 Runtime 链扩展中 `TRANSFER_CERT_FUNC_ID = 2` 只返回 unsupported 状态，无法从合约侧触发权证转移。第二篇论文若强调数据使用权流通，必须补齐该能力。

### 4.2 修改范围

主要文件：

- `runtime/src/asset_market_extension.rs`
- `contracts/market_standard/lib.rs`
- `pallets/dataassets/src/lib.rs`
- `pallets/dataassets/src/tests.rs`
- `contracts/market_orderbook/lib.rs`

### 4.3 设计内容

新增或补齐合约调用 Runtime 转移权证的接口。

建议 Chain Extension 输入为：

```text
(asset_id, certificate_id, to_account)
```

Runtime 通过合约调用者地址识别市场账户或当前持有人，并调用 `pallet-dataassets` 内部权证转移逻辑。

如果需要更强的权限控制，可采用：

```text
(asset_id, certificate_id, from_account, to_account)
```

并要求 Runtime 校验 `from_account` 与权证当前持有人一致，且市场已获得授权。

### 4.4 验收标准

- 合约可调用 `transfer_certificate` 链扩展。
- 权证当前持有人可通过市场转移权证给买方。
- 非持有人、证书不存在、证书已撤销或已过期时转移失败。
- 失败时不产生权证状态变化。
- `pallet-dataassets`、`market-standard`、相关 runtime 测试通过。

## 5. 阶段 2：完善市场订单状态机

### 5.1 目标

将当前订单的 `active: bool` 扩展为完整交易状态机，使市场合约能够支撑论文中的上架、购买、结算、撤单和失败恢复分析。

### 5.2 修改范围

主要文件：

- `contracts/market_orderbook/lib.rs`
- `contracts/market_standard/lib.rs`

### 5.3 订单状态

建议定义：

```text
Listed
Locked
Settled
Cancelled
Failed
```

含义：

- `Listed`：订单已上架，可被购买。
- `Locked`：订单正在结算，防止重复购买。
- `Settled`：订单已完成结算。
- `Cancelled`：卖方已撤单。
- `Failed`：结算失败，订单保留或进入可恢复状态。

### 5.4 订单字段

建议订单结构包含：

```text
seller
buyer
price
asset_type
asset_id
certificate_id
right_type
status
created_at
settled_at
```

其中：

- `asset_type` 区分元证交易和权证交易。
- `certificate_id` 仅在权证订单中使用。
- `right_type` 可用于表示使用权或访问权。

### 5.5 交易流程

购买流程建议为：

```text
检查订单存在
检查订单状态为 Listed
检查支付金额
将订单状态置为 Locked
调用 Chain Extension 完成 Runtime 权属结算
向卖方付款
更新订单状态为 Settled 或删除订单
发送成交事件
```

失败处理：

- 支付不足：直接失败，不改变订单状态。
- Runtime 结算失败：订单恢复为 `Listed` 或进入 `Failed`。
- 付款给卖方失败：不得产生错误的成功结算记录。
- 撤单失败不得使用 `panic!`，应返回明确错误。

### 5.6 验收标准

- 支持元证订单和权证订单。
- 重复上架被拒绝。
- 支付不足被拒绝。
- Chain Extension 失败时订单不被错误删除。
- 成功购买后订单状态正确变化。
- 撤单逻辑返回错误而不是 panic。

## 6. 阶段 3：增加链上交易结算记录

### 6.1 目标

为论文中的交易一致性、可追责性和实验统计提供统一链上证据。

当前系统已有 `AssetTransferred` 和 `CertificateTransferred` 等事件，但缺少面向交易链的统一结算记录。建议增加交易结算事件，必要时增加持久化存储。

### 6.2 修改范围

主要文件：

- `pallets/dataassets/src/lib.rs`
- `pallets/dataassets/src/types.rs`
- `runtime/src/asset_market_extension.rs`
- `pallets/markets/src/lib.rs`

### 6.3 结算事件

建议新增事件：

```text
TradeSettled {
    trade_id,
    market,
    seller,
    buyer,
    asset_id,
    certificate_id,
    asset_type,
    price,
    settled_at
}
```

其中：

- `certificate_id` 对元证交易可为空或全零。
- `asset_type` 表示 `DataAsset` 或 `Certificate`。
- `market` 为触发结算的市场合约账户。

### 6.4 trade_id 生成

建议生成规则：

```text
trade_id = hash(market, buyer, asset_id, certificate_id, block_number, nonce)
```

该规则保证同一市场内交易具有可区分性，便于实验统计和链上追踪。

### 6.5 验收标准

- 元证交易成功后产生 `AssetTransferred` 和 `TradeSettled`。
- 权证交易成功后产生 `CertificateTransferred` 和 `TradeSettled`。
- 失败交易不产生 `TradeSettled`。
- `TradeSettled` 包含足够字段用于论文实验统计。

## 7. 阶段 4：打通市场统计与激励

### 7.1 目标

将数据交易链的真实成交行为接入激励系统，使市场运营者、交易者和数据资产能够基于交易行为获得统计和奖励。

### 7.2 修改范围

主要文件：

- `pallets/shared_traits/src/lib.rs`
- `pallets/incentive/src/lib.rs`
- `pallets/markets/src/lib.rs`
- `runtime/src/configs/mod.rs`
- `runtime/src/asset_market_extension.rs`

### 7.3 需要补充的接口

建议扩展 `IncentiveHandler`：

```text
register_market_volume(market, amount)
register_trader_volume(trader, amount)
distribute_liquidity_reward(recipient, order_amount)
```

市场交易成功后记录：

- 数据资产交易次数。
- 市场月交易额。
- 买方月交易额。
- 可选：卖方收入统计。

### 7.4 修复现有 placeholder

当前 `pallet-incentive` 的优质市场奖励逻辑中存在通过 `market_id` 直接解码运营者账户的 placeholder。应改为：

```text
market_id / market_account -> pallet-markets::RegisteredMarkets -> creator/operator
```

确保奖励发给真实市场运营者。

### 7.5 验收标准

- 市场成交后 `MarketMonthlyVolume` 更新。
- 市场成交后 `TraderMonthlyVolume` 更新。
- 月度优质市场奖励发给真实市场运营者。
- 激励池余额不足时交易本身不被错误中断。
- 相关 incentive 和 markets 测试通过。

## 8. 阶段 5：补充轻量交付证明闭环

### 8.1 目标

为论文提供“链下数据交付可追踪”的最小闭环，但不在第二篇中过度展开完整存储链问题。

### 8.2 设计边界

当前 `pallet-storage_ipfs` 是原型模块，尚未接入 Runtime。第二篇论文主线是数据交易链，不建议第一阶段就实现完整存储链或复杂 IPFS 可用性证明。

建议先实现轻量交付确认机制：

- 数据资产注册时保留 `metadata_cid`、`data_cid`、`encryption_info`。
- 交易结算后，买方可提交 `delivery_hash` 或交付确认。
- Runtime 记录交付确认事件，用于证明买方已获得链下访问材料或交付凭据。

### 8.3 可选接口

建议新增：

```text
confirm_delivery(asset_id, certificate_id, delivery_hash)
```

或在市场合约中增加：

```text
report_delivery(trade_id, delivery_hash)
```

### 8.4 验收标准

- 买方可以基于元证或权证查询链下数据 CID 和加密信息。
- 成交后可记录交付确认事件。
- 交付确认与 `trade_id` 或 `asset_id/certificate_id` 可关联。
- 不要求实现真实 IPFS 下载验证。

## 9. 阶段 6：建立第二篇论文实验套件

### 9.1 目标

建立 `paper_exp/paper2_exp` 实验目录，为第二篇论文提供可复现实验数据。

### 9.2 目录建议

```text
paper_exp/paper2_exp/
  README.md
  scripts/
  tests/
  results/
  exp1_trade_cost/
  exp2_settlement_consistency/
  exp3_certificate_market_scalability/
  exp4_incentive_accounting/
```

### 9.3 实验 1：交易开销实验

目的：比较不同数据交易实现的交易成本。

对比组：

- Ethereum Solidity 数据市场。
- Substrate ink! 合约数据市场。
- AssetXChain 合约-运行时协同交易链。

指标：

- 交易延迟。
- 交易费用或 weight。
- 状态写入次数。
- 成交成功率。

### 9.4 实验 2：结算一致性实验

目的：验证合约订单状态和 Runtime 权属状态不会发生不一致。

异常场景：

- 未授权市场购买。
- 支付不足。
- 重复购买。
- Runtime 转移失败。
- 订单撤销后购买。
- 权证非持有人转移。

指标：

- 错误拒绝率。
- 状态残留数量。
- 错误结算数量。
- 授权清理正确性。

### 9.5 实验 3：权证市场扩展实验

目的：测试同一数据资产派生大量 RightToken 后的交易能力。

变量：

- 权证数量。
- 买方数量。
- 权证转移次数。
- 权证有效期分布。

指标：

- 权证发行耗时。
- 权证交易耗时。
- 权证撤销耗时。
- 平均交易成本。

### 9.6 实验 4：激励统计实验

目的：验证交易链成交行为能被激励模块正确统计。

指标：

- 资产交易次数。
- 市场月交易额。
- 交易者月交易额。
- 市场奖励发放正确性。
- 激励池余额变化。

### 9.7 验收标准

- 每个实验有 README。
- 每个实验有 runner 脚本。
- 每个实验输出 CSV。
- 每个实验有 summary 脚本或测试校验。
- 输出字段能直接服务论文表格和图。

## 10. 阶段 7：打通合约订单状态与 Runtime 结算一致性闭环

### 10.1 目标

补齐阶段 2 遗留风险：订单状态机当前主要存在于市场合约内，尚未与 Runtime 的可信结算记录、权属状态和 `trade_id` 形成可验证的一致性闭环。
例如：当前合约是先完成 Runtime 权属变更/发行，再给卖方付款；如果后续付款失败，订单会标记 Failed，但 Runtime 状态已经变化。这是后续“合约订单状态与Runtime 结算一致性闭环”阶段仍需要继续补齐的风险。

本阶段目标是让论文中的“合约负责交易逻辑、Runtime 负责可信结算”不仅停留在模块分工上，还能通过链上记录证明：

```text
合约订单 Settled <-> Runtime 权属已变更 <-> Runtime TradeSettled 已记录
合约订单 Failed/Cancelled <-> Runtime 不产生错误成功结算记录
```

### 10.2 修改范围

主要文件：

- `contracts/market_orderbook/lib.rs`
- `contracts/market_standard/lib.rs`
- `runtime/src/asset_market_extension.rs`
- `pallets/dataassets/src/lib.rs`
- `pallets/dataassets/src/types.rs`
- `pallets/dataassets/src/tests.rs`
- 必要时补充 `runtime` 或合约测试。

### 10.3 设计内容

在阶段 3 的 `TradeSettled` 记录基础上，建立合约订单与 Runtime 结算记录的关联字段。

建议补充：

```text
order_id
trade_id
market_account
seller
buyer
asset_type
asset_id
certificate_id
price
order_status
runtime_settlement_status
```

其中：

- `order_id` 由市场合约生成并存入订单。
- `trade_id` 由 Runtime 生成后返回给市场合约，或由合约与 Runtime 使用一致规则共同派生。
- 市场合约在订单 `Settled` 时必须保存 `trade_id`。
- Runtime `TradeSettled` 必须包含足够字段反查市场订单。

若当前 Chain Extension 只能返回 `Result<(), Error>`，建议扩展为返回结算结果：

```text
SettlementResult {
    trade_id,
    settled_at,
}
```

或在保持接口兼容的前提下，新增查询接口：

```text
get_last_settlement(order_id)
get_trade_settlement(trade_id)
```

### 10.4 原子性与失败处理

必须明确合约支付和 Runtime 权属变更之间的原子性边界。

建议采用以下最小策略：

- 订单进入 `Locked` 后才能调用 Runtime 结算。
- Runtime 结算成功但卖方收款失败时，不得把订单标记为 `Settled`。
- 若运行环境无法保证合约返回错误会回滚 Chain Extension 写入，则不得在“付款给卖方”之后留下已经转移的错误权属状态。
- 优先考虑将“权属变更 + 结算记录 + 必要支付确认”收敛到单一可信结算入口，减少合约状态与 Runtime 状态分叉。
- 失败订单必须能通过 `order_id/trade_id` 判断是否已产生 Runtime 成功结算记录。

### 10.5 一致性检查接口

建议补充只读检查能力，用于实验和追责：

```text
check_order_settlement(order_id) -> ConsistencyStatus
```

状态建议包括：

```text
ConsistentSettled
ConsistentFailed
MissingRuntimeSettlement
UnexpectedRuntimeSettlement
OwnershipMismatch
PaymentMismatch
```

该接口可先放在测试辅助逻辑或实验脚本中，不要求第一版做成完整链上公开接口。

### 10.6 验收标准

- 成功购买元证后，市场订单为 `Settled`，订单保存 `trade_id`，Runtime 权属已变更，并存在对应 `TradeSettled`。
- 成功购买权证后，市场订单为 `Settled`，订单保存 `trade_id`，Runtime 权证持有人已变更，并存在对应 `TradeSettled`。
- Runtime 结算失败时，市场订单为 `Failed` 或恢复为 `Listed`，不得产生 `TradeSettled`。
- 卖方收款失败时，市场订单不得为 `Settled`，且不得留下不可解释的成功结算记录。
- 撤单后订单为 `Cancelled`，不得产生 `TradeSettled`。
- 重复购买、重复结算、重复 `trade_id` 被拒绝。
- 至少有一组测试或实验脚本能批量校验合约订单、Runtime 权属和 Runtime 结算记录的一致性。

## 11. 推荐实施顺序

推荐顺序：

1. 阶段 1：权证 Chain Extension。
2. 阶段 2：市场订单状态机。
3. 阶段 3：交易结算记录。
4. 阶段 4：市场统计与激励。
5. 阶段 7：合约订单状态与 Runtime 结算一致性闭环。
6. 阶段 6：论文实验套件。
7. 阶段 5：轻量交付证明闭环。

将阶段 5 放后，是因为链下存储和交付容易扩展成独立存储链问题，会分散第二篇论文的主线。第二篇应优先保证数据交易链闭环。

## 12. 第一轮最小实现范围

第一轮建议只完成核心闭环：

- 实现权证 Chain Extension。
- 合约订单支持元证和权证两类交易。
- 增加交易结算事件。
- 建立订单 `trade_id` 与 Runtime 结算记录的关联。
- 补充关键单元测试。

第一轮完成后，项目即可支撑论文核心创新：

```text
市场合约负责交易撮合，Runtime 负责元证/权证可信结算。
```

## 14. 风险与边界

- 当前工作区已有未提交改动，实施前需要先检查 diff，避免覆盖已有工作。
- 权证交易 Chain Extension 的权限模型需要明确，否则容易出现市场越权转移权证。
- 市场合约和 Runtime 之间必须保证失败回滚语义清晰，不能出现付款成功但权属未变更。
- 市场订单状态不能只停留在合约内，必须能通过 `trade_id` 与 Runtime 权属和结算记录交叉验证。
- 激励模块不能让奖励发放失败阻断正常交易。
- `storage_ipfs` 暂时不作为第二篇核心实现，除非论文明确要覆盖链下存储可用性。

## 15. 论文对应关系

项目补充完成后，可支撑第二篇论文的以下章节：

- 系统模型：角色、元证、权证、市场、交付凭据。
- 架构设计：权属层、交易层、结算层。
- 核心机制：合约-运行时协同结算、元证/权证分离交易、市场授权与追责。
- 安全分析：无越权交易、无重复结算、失败不产生错误结算记录。
- 实验评估：交易开销、一致性异常、权证扩展、激励统计。
